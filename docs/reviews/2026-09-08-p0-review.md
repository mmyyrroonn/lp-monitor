## 总体结论

工程纪律高于常见的一次性工具：证据链、凭据隔离、只读方法白名单、"不支持 ≠ 超时"的三态能力分类都是真做。凭据隔离用真实 viem 错误对象验证过：viem 错误 message 确实内嵌完整 URL，但 `classifyRpcError` 所有分支返回的 message 恒为 `RPC <kind>`，已提交的 requests.jsonl 中 grep 不到任何 URL 或 token。V4 poolId 与官方 v4-sdk 在非零 hooks 加动态费率 0x800000 的真实用例上逐位一致。

架构核心问题：**P0 的每个抽象都是"单次有界运行"的形状，没有一个能直接承载 P1 的长跑追块进程。** 预算与限流在 schema 层焊死上限且 429 惩罚永不衰减；证据 manifest 写绝对路径，换机器即失效；rpc 与 ops 双向依赖，设计文档承诺的 ingest / storage / registry 目录一个都不存在。

## 阻塞项（进入 P1 前必须处理）

### B1 限流惩罚永不衰减，一次 429 后整个进程钉死在 1 RPC/s [阻塞][已核实]

- 位置：`src/rpc/rate-limit.ts:10,16`
- 证据：`penaltyMs = Math.max(1000, this.penaltyMs)` 首次 429 置为 1000 ms，之后既不指数增长也不恢复；`acquire()` 每次取 `max(penaltyMs, 1000/perSecond)`。P0 实测 capture 86 次调用耗时 83.7 秒，即触发 429 后被永久压到约 1 次/秒。P1 每 2 秒追块的稳态需求约 4 次/秒（`docs/research/2026-09-08-logs-first-heat.md:57`），结果是永久 head lag 且无法自愈。
- 另：构造器硬性 `perSecond <= 5` 抛 RangeError（`rate-limit.ts:7`），schema 同样 `.max(5)`。P6 计划要求按付费端点额度调整，代码会拒绝。
- 建议：改 token bucket + 指数退避 + 连续 N 次成功后线性衰减恢复；5 RPS 从类型上限降为默认值；区分 live 与 backfill 两个桶（`docs/research/2026-09-08-rpc-only-cost.md:43` 已定义 `maxBackfillRpcRps`，代码里没有这个概念）。

### B2 预算上限焊死在 schema 里，P1 的 follow 连配置都写不出来 [阻塞][已核实]

- 位置：`src/config/chain.ts:12-14`，`src/ops/request-meter.ts:6,9,16`
- 证据：`maxRpcCalls` 最大 150、`rpcPerSecond` 最大 5、`timeoutMs` 最大 10000、`pollIntervalMs` 是 `z.literal(2000)`。P1 计划的 `follow --duration 10m` 约 300 批 × 3 次调用 ≈ 900 次。`RequestMeter.callTimes` 无界增长，`summary()` 的 peakOneSecond 是 O(n²) 且每次 slice 分配；`src/rpc/identity.ts:114` 为读一个计数器调用了整个 `summary()`。
- 建议：RequestMeter 拆为固定容量环形缓冲的滑动窗口速率观测器 + 可选的一次性配额闸门；`maxRpcCalls` 改 `number | null`，150 降级为 config 取值而非类型上限；`pollIntervalMs` 改为带默认值的 number。

### B3 manifest 记录绝对 Windows 路径，集成测试与验收脚本换机器必然失败 [阻塞][已核实]

- 位置：`src/ops/files.ts:6-8`，`src/ops/fixture-capture.ts:116,149-151`，消费方 `tests/integration/p0-fixtures.test.ts:20`、`scripts/p0-acceptance.mjs:27`
- 证据：manifest 的 `files[].path` 全部是 `E:\\lp-monitor\\artifacts\\...`。raw 目录已被强制提交进版本库（与 .gitignore 冲突），任何人 clone 后：测试用相对路径找到 manifest，不 skip；再按绝对 path 读文件，ENOENT，测试红而不是优雅 skip。`p0-acceptance.mjs:36` 是全吞式 catch，会把路径错误报成"验收输入不完整"。把整个 run 目录复制到临时目录后复现：6 个 path 仍指向原机器。
- 建议：`saveJson` 返回相对 runDir 的 POSIX 路径（`scripts/vendor-abis.mjs:56` 已这么做，照抄）；消费端 `join(runRoot, file.path)`；acceptance 脚本 catch 补 `e.message`。

### B4 供应商限流码被判成 range-limit：不降速，反而对已限流端点做区间二分放大 [阻塞][已核实]

- 位置：`src/rpc/errors.ts:18-22`，`src/rpc/client.ts:53`，`src/ops/fixture-capture.ts:26-28`
- 证据：用真实 viem 错误对象跑分类：
  - `RpcRequestError -32005 "limit exceeded"` → `range-limit`，不可重试（Alchemy / Infura 类端点的典型限流文案）
  - `RpcRequestError -32005` 带 CU/sec 文案 → `request-failed`，不可重试
  - `HttpRequestError status 503` → `request-failed`，不可重试，配置的 `maxRetries: 2` 在最常见瞬时故障上不生效
  - `HttpRequestError status 500, url 含 "429"` → `rate-limit`（第 18 行 `/429/` 对拼接了完整 URL 的字符串做子串匹配）
- 判成 range-limit 后 `penalize()` 不触发，`fetchBoundedLogs` 把区间拆半再发两次，对已限流端点形成放大，150 次预算被快速吃光。
- 建议：重排为先看结构化字段（`code` / `status`），message 正则只作兜底；限流分支加 `code === -32005 || code === -32029` 并前置于 range-limit；`limit exceeded` 从 range-limit 正则移除或仅限 getLogs 语境；5xx（除 501）与 408 归入可重试；429 只看 status 数值。

### B5 每次请求同步追加完整响应体到证据文件，无开关 [阻塞][已核实]

- 位置：`src/rpc/client.ts:39`，`src/cli.ts:45-46`
- 证据：已提交的 requests.jsonl 为 757,665 字节 / 86 行，平均 8.8 KB/次调用。按 1.5 次/秒外推约 1.1 GB/天。`appendFileSync` 在事件循环上阻塞。cli 无条件传入 evidenceFile。
- 建议：三档策略 full / sampled / off，按运行分片轮转，改异步批量写；follow 默认只落 method / params / hash / elapsed，不落完整 result。

### B6 @types/better-sqlite3 落后运行时 4 个大版本 [阻塞][已核实]

- 位置：`package.json:17,20`
- 证据：运行时 better-sqlite3 13.0.3，类型包 9.6.0。P1 Task 1.1 就要写 SQLite store，新增 options 与变更签名不会被 strict 捕获。
- 建议：对齐到匹配 v13 的类型版本，或改用包自带类型（若 v13 已内置）。

### H2 地址与 hash 未在传输边界统一小写 [中][已核实]

- 位置：`src/rpc/client.ts:81-84`，`src/ops/fixture-capture.ts:40,56,64`，`src/config/chain.ts:5`

- 位置：`tsconfig.json`，`package.json` scripts
- 证据：无 .github、无 lint script、无格式化配置。tsconfig 的 `scripts/**/*.ts` 匹配 0 个文件，三个 .mjs 脚本（含验收闸门 p0-acceptance.mjs）完全脱离类型检查。`rootDir: "."` 加 include tests 让 `pnpm build` 把测试编进 dist/tests（README 因此要写 `node dist/src/cli.js`）。同一仓库两种代码风格：resolve-time.ts 舒展多行，cli.ts / fixture-capture.ts 高度压缩单行。

### H6 预算与限流失败被降级成 request-failed，诊断信息丢失 [中]

- 位置：`src/ops/fixture-capture.ts:24-31`，`src/rpc/capabilities.ts:67`，`src/rpc/client.ts:56`，`src/rpc/rate-limit.ts:14-18`

- 建议：budget / rate-limit 从 fetchBoundedLogs 直接向上抛；退避统一由 RateLimiter 承担；acquire 改为可配置并发的信号量。

## 测试缺口（按价值排序）
